## 3. Development-only механизмы в Production

Проверено 24.10.2026 скриптом `infrastructure/scripts/production-smoke.sh`: release-сборка API, окружение
`Production`, временная база, одноразовые секреты.

| Проверка | Результат |
|---|---|
| Запуск без ключа JWT | API не стартует («The SigningKey field is required») |
| Вход `1`/`1` (dev-логин) | 400 `validation_failed` |
| Вход по телефону dev-аккаунта `+998000000001` / `1` | 401 `invalid_credentials`; dev-аккаунтов в базе 0 |
| Swagger | 404 |
| SMS-код в лог (`DevelopmentSmsSender`) | не регистрируется; без провайдера SMS-endpoints возвращают 503 (тест `AuthTests`) |
| Первый администратор | создан из конфигурации, при входе обязательна смена пароля, до смены admin-API → 403 |
| Пароли и токены в логе | не найдены |
| Мобильное приложение | короткий логин только в debug-сборке (`kDebugMode`) |
| Тестовые учётные данные в коде | только в `DevLogins.cs` (Development) и в тестах |

Риски, которые нужно закрыть при развёртывании (подробно в OPERATIONS.md, раздел 5):
- запуск боевого API с `ASPNETCORE_ENVIRONMENT=Development` включил бы dev-механизмы — запрещено инструкцией;
- боевую базу создавать с нуля, не копией dev-базы.

## 4. Сценарий демонстрации заказчику

**Подготовка (за день).** Отдельная демонстрационная база; данные реальных клиентов, боевые секреты и
dev-конфигурация не используются (подробный чек-лист — `docs/CLIENT_DECISIONS.md`, раздел 9).
1. Пустая база и API в окружении, близком к боевому: администратор создан из `Bootstrap__*`, его временный
   пароль уже заменён. Dev-логины `1`/`2`/`3` на демонстрации **не использовать**.
2. Тренер «Дилшод Рашидов» создан в панели, пароль сменён; в его карточке указана специализация.
3. План «Безлимит 30 дней» создан.
4. Устройства: телефон клиента (iOS или Android) и телефон тренера с установленным приложением, собранным
   с `API_URL`; браузер с панелью.

**Ход (≈15 минут).** Каждый шаг повторяет автоматические сквозные тесты, которые проходят: Playwright
`priority-scenario.spec.ts` и мобильный `integration_test/e2e_test.dart` на iOS и Android.

## 5. Известные ограничения и функции этапа 2

### Этап 2 (п. 3.1 договора) — намеренно не реализовано
| Функция | Состояние в этапе 1 |
|---|---|
| Click и Payme | Нет. Платежей в модели нет; отчёты без финансов |
| SMS-подтверждение | Интерфейс `ISmsSender` и endpoints подтверждения есть; без провайдера — 503 |
| Турникет | Посещения вводятся администратором вручную (`VisitSource.Manual`) |
| Автопродление абонементов | Нет |
| Push-уведомления и массовые рассылки | Только внутренние уведомления в приложении |
| Промокоды и скидки | Нет |

### Вне договора (п. 1.3)
Фитнес-бар, продажа товаров, 1С — не реализуются.

### Ограничения этапа 1
1. Правила тренировок не утверждены (7 вопросов в PROGRESS.md): тренировка без абонемента разрешена с
   предупреждением; проведённая тренировка не считается посещением; отменяет только тренер; пересечения
   у разных тренеров не проверяются; общего расписания клуба нет.
2. Нет управления учётными записями администраторов и ролей персонала в панели.
3. Нет страницы тренировок в панели (API есть).
4. Нет выгрузки отчётов в файлы.
5. Нет светлой темы и английского языка (архитектура позволяет добавить).
6. Ограниченные списки без подгрузки: предстоящие тренировки клиента — до 100; заявки клиента — последние 50.
7. Ограничение частоты входа считается по IP; за обратным прокси требуется доработка (`ForwardedHeaders`).
8. Release-сборки мобильного приложения требуют `--dart-define=API_URL=…`.
9. Не проверено: физический iPhone (нет Apple ID в Xcode), физический Android-телефон, планшеты,
   нагрузка, тест на проникновение, публикация в App Store / Google Play (не входит в п. 2.1).

**Подтверждено** (реализовано и проверено тестами и демонстрацией): регистрация и вход по телефону,
профиль клиента, абонементы (просмотр клиентом, управление администратором), выбор тренера и заявки,
кабинет тренера, панель администратора по клиентам и тренерам, базовая статистика и отчёты, серверная
часть и база данных, безопасность Production-режима, резервное копирование.

**Требует уточнения у заказчика:**
1. Какой документ является согласованным ТЗ (найденный файл ТЗ относится к другому проекту).
2. Нужны ли макеты дизайна отдельно от реализованного приложения.
3. «Заявка на занятия»: достаточно ли заявки на тренера и назначения тренировок тренером, или нужна
   самостоятельная запись клиента; 7 правил по тренировкам.
4. Управление учётными записями администраторов и персонала.
5. Состав отчётов: выгрузка в файлы; финансовые показатели (по онлайн-оплатам — этап 2, ручной учёт
   оплат — отдельное соглашение).
6. Нужен ли запуск на сервере в рамках этапа 1.
7. Критерии приёмки на физических устройствах.

Варианты и предварительные оценки по каждому пункту — `docs/CLIENT_DECISIONS.md`.

**До подписания акта:** подписать договор и утвердить ТЗ; получить письменные решения по `docs/CLIENT_DECISIONS.md`;
провести демонстрацию; проверить на физических устройствах; закрыть или письменно перенести пункты
«требует уточнения». Если в приёмку входит запуск на сервере — развернуть по OPERATIONS.md с доработкой
`ForwardedHeaders`.
