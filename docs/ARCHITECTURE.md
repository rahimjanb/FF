# Архитектура

## Компоненты

```
mobile (Flutter) ──┐
                   ├──HTTPS/JSON──> backend (ASP.NET Core 10) ──EF Core──> PostgreSQL
admin (React)   ───┘
```

Вся бизнес-логика и проверка прав находятся в backend. Мобильное приложение и веб-панель только
отображают данные и отправляют команды. Логика не дублируется: например, статус абонемента всегда
вычисляет сервер (`effectiveStatus`).

### Backend: `backend/src/FitnessFormulasi.Api`

| Папка | Назначение |
|---|---|
| `Domain/` | Сущности, перечисления, `MembershipStatusCalculator` |
| `Data/` | `AppDbContext` (связи, индексы, ограничения), миграции, `DbInitializer` (миграции и первый администратор) |
| `Auth/` | JWT, refresh-токены, вход и регистрация, `ISmsSender` |
| `Common/` | Единый формат ошибок, пагинация, часы клуба, текущий пользователь, нормализация телефона |
| `Features/` | Сервисы (абонементы, заявки, тренировки, уведомления) и контроллеры клиента и тренера |
| `Features/Admin/` | Контроллеры администратора, dashboard и отчёты |

### Мобильное приложение: `mobile/lib`

| Папка | Назначение |
|---|---|
| `core/` | `ApiClient` (обновление токенов), безопасное хранилище токенов, конфигурация, валидаторы |
| `data/` | Модели (DTO) и репозитории — единственный слой работы с API |
| `state/` | Сессия (`SessionController`) и язык (`LocaleController`) |
| `ui/` | Тема, общие виджеты, экраны клиента (`client/`) и кабинета тренера (`trainer/`) |
| `l10n/` | ARB-файлы `ru` (основной) и `uz` |

После входа приложение выбирает интерфейс по роли: `Client` — приложение клиента, `Trainer` —
кабинет тренера. Администраторы работают только в веб-панели.

### Веб-панель: `admin/src`

`api/` — HTTP-клиент и типы, `auth/` — сессия, `pages/` — страницы, `components/` — общие элементы
интерфейса, `lib/` — форматирование и хуки.

## Модель данных

| Сущность | Ключевые поля и правила |
|---|---|
| `Role` | Admin / Trainer / Client (сидируются миграцией). У пользователя одна роль |
| `User` | Телефон в формате E.164 (уникальный), PBKDF2-хеш пароля, статус Active/Blocked, флаг `MustChangePassword`, счётчик неудачных входов, блокировка по времени |
| `RefreshToken` | Хранится только SHA-256 хеш. Ротация, цепочка `ReplacedByTokenId` |
| `PhoneVerificationCode` | Хеш кода, срок 5 минут, не более 5 попыток (подготовка к этапу 2) |
| `ClientProfile` | 1:1 с `User`, закреплённый тренер (`AssignedTrainerId`), служебные заметки (видны только администратору) |
| `TrainerProfile` | 1:1 с `User`, специализация, опыт, флаги «набирает клиентов» и «активен» |
| `MembershipPlan` | Unlimited или LimitedVisits, срок в днях, лимит посещений, цена (справочно). CHECK-ограничения |
| `Membership` | Клиент, план, `StartDate` и `EndDate` (даты клуба, конец включительно), статус Active/Frozen/Cancelled, снимок лимита посещений, `xmin` для конкурентного доступа |
| `TrainerRequest` | Pending/Accepted/Rejected/Cancelled. Частичный уникальный индекс: одна ожидающая заявка на пару «клиент — тренер» |
| `TrainingSession` | Тренер, клиент, начало (UTC), длительность 15–480 минут, статус |
| `Visit` | Клиент, абонемент, время, источник (`Manual`; турникет — этап 2) |
| `Notification` | Тип, связанный объект, `Payload`. Текст локализует клиентское приложение |

У всех сущностей есть `Id` (UUID v7), `CreatedAt` и `UpdatedAt`; временные метки выставляет `AppDbContext`.
Внешние ключи настроены с `Restrict`, поэтому каскадного удаления бизнес-данных нет.

## Бизнес-правила

- **Статус абонемента** вычисляется по дате клуба (Asia/Tashkent) в `MembershipStatusCalculator`.
  Порядок проверок: Cancelled → Expired (дата позже `EndDate`) → Frozen → Upcoming → Exhausted
  (лимит посещений) → Active. Истёкший абонемент никогда не считается активным.
- **Назначение абонемента**: `EndDate = StartDate + DurationDays − 1`. Пересечение с другим
  неотменённым абонементом клиента запрещено. Гонку исключает блокировка строки клиента
  (`SELECT … FOR UPDATE`). Изменения плана не затрагивают уже выданные абонементы.
- **Заявка на тренера**: тренер должен быть активен и набирать клиентов. Повторная ожидающая
  заявка запрещена дважды: проверкой в коде и уникальным индексом в БД (параллельные запросы →
  409). При принятии клиент закрепляется за тренером, а остальные ожидающие заявки клиента
  автоматически отменяются.
- **Тренировки**: тренер назначает их только своим клиентам и только на будущее время. Пересечение
  с другими тренировками тренера запрещено. Провести можно только начавшуюся тренировку; изменить
  можно только запланированную.
  - Клиент: `GET /api/me/training-sessions?scope=Upcoming` — запланированные и ещё не закончившиеся,
    ближайшие первыми; `scope=History` — закончившиеся, проведённые и отменённые, свежие первыми
    (постранично). Тренировка, которая уже идёт, остаётся в предстоящих.
  - Тренер: `GET /api/trainer/sessions` по умолчанию возвращает период «7 дней назад — 30 дней вперёд»,
    чтобы неотмеченные прошедшие тренировки можно было провести или отменить. В приложении они помечены
    «Прошла» и «Нажмите, чтобы отметить результат».
  - Отсутствие действующего абонемента тренировки не блокирует: клиент видит предупреждение, тренер —
    предупреждение при создании. Нужно ли это ограничение, ещё предстоит согласовать (см. PROGRESS.md).
- **Актуальность данных в приложении**: вкладки перезагружают данные при каждом переключении, экраны
  с `AsyncView` — при возврате приложения из фона, плюс pull-to-refresh.
- **Посещение** (вводит администратор) привязывается к абонементу, действующему в этот день. Без
  действующего абонемента или при исчерпанном лимите → 409.
- **Часовой пояс**: в БД хранятся даты (`date`) и моменты в UTC. «Сегодня» вычисляет `IClubClock`
  (`Club:TimeZoneId`). Веб-панель и приложение показывают время клуба.

## Безопасность

- **Аутентификация**: телефон и пароль. Хеширование — `PasswordHasher<T>` из ASP.NET Identity
  (PBKDF2). Access-токен JWT живёт 15 минут. Refresh-токен действует 30 дней с ротацией: повторное
  использование уже ротированного токена отзывает все сессии пользователя.
- **Временные пароли**: если пароль задал персонал (клиент или тренер создан администратором, пароль
  сброшен, первый администратор из конфигурации), у пользователя ставится `MustChangePassword`. Пока
  флаг стоит, `PasswordChangeGate` отвечает `403 password_change_required` на всё, кроме `/api/auth/me`,
  `change-password` и `logout`. Мобильное приложение и веб-панель в этом случае показывают только экран
  смены пароля. `change-password` снимает флаг, завершает остальные сессии и выдаёт новую пару токенов.
- **Защита входа**: блокировка на 15 минут после 5 неудачных попыток, rate limiting `/api/auth/*`
  по IP, одинаковая ошибка для неизвестного номера и неверного пароля.
- **Авторизация** только на сервере: `[Authorize(Roles = ...)]` на каждом контроллере. При каждом
  запросе проверяется, что пользователь активен и роль не изменилась, поэтому блокировка действует
  сразу.
- **Изоляция данных**: id клиента или тренера берётся из токена, а не из запроса. Чужие объекты
  для тренера и клиента возвращают 404 — существование не раскрывается. Тренер не видит служебных
  заметок, клиент не видит контактов тренеров.
- **Секреты**: только через переменные окружения или `dotnet user-secrets`. В `appsettings.json`
  секретов нет; без `Jwt:SigningKey` (не короче 32 символов) и строки подключения API не запускается.
- **Логи** не содержат паролей, токенов и SMS-кодов (кроме явно помеченного Development-отправителя, см. ниже).
- **Хранение токенов**: в мобильном приложении — Keychain/Keystore (`flutter_secure_storage`).
  В веб-панели access-токен хранится в памяти, refresh-токен — в `sessionStorage` и удаляется при закрытии вкладки.
- **HTTP без TLS** разрешён только для разработки: Android — `usesCleartextTraffic` в debug-манифесте,
  iOS — `NSAllowsLocalNetworking`. В Production нужен HTTPS за обратным прокси.

## Development-only механизмы (явно помечены)

| Что | Где | Почему безопасно |
|---|---|---|
| `DevelopmentSmsSender` пишет SMS-код в лог | `Auth/Sms.cs` | Регистрируется только при `ASPNETCORE_ENVIRONMENT=Development` и бросает исключение в другом окружении. В Production используется `NotConfiguredSmsSender`: SMS-endpoints возвращают 503 |
| Swagger UI | `Program.cs` | Включается только в Development |
| Автоматическое применение миграций | `Database:MigrateOnStartup` | По умолчанию `false`, включено в `appsettings.Development.json` и в compose-профиле `api` |
| Тестовый HTTP-backend | `mobile/test/fake_backend.dart` | Находится в `test/`, в приложение не попадает |
| Короткие логины `1`/`1`, `2`/`2`, `3`/`3` и их аккаунты | `Auth/DevLogins.cs`, `core/validators.dart` | Сервис `DevLogins` регистрируется только в Development; без него логин «1» отклоняется валидацией, аккаунты не создаются (тест `Short_dev_logins_are_rejected_outside_development`, проверка `infrastructure/scripts/production-smoke.sh`). Приложение принимает короткий логин только в debug-сборке. Аккаунты имеют телефоны `+99800000000x`: боевую базу создавать с нуля, не копировать из dev |

## Точки расширения (этап 2)

- **SMS**: реализовать `ISmsSender` для провайдера (Eskiz, Play Mobile и т. п.) и зарегистрировать
  в `Program.cs`. Endpoints `/api/auth/phone-verification/*` уже готовы.
- **Турникет**: добавить значение в `VisitSource` и сервис, создающий `Visit`. Решение о проходе —
  через `MembershipStatusCalculator`.
- **Платежи (Click/Payme)**: отдельная сущность `Payment`, связанная с `Membership`. Поле `MembershipPlan.Price`
  уже есть.
- **Push**: отправка из `NotificationService` (сейчас уведомления только внутри приложения).
- **Английский язык**: файл `mobile/lib/l10n/app_en.arb` и строка в `LocaleController.supported`.
- **Светлая тема**: палитра собрана в `mobile/lib/ui/theme.dart` (`AppColors`).
