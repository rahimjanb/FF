# Архитектура

## Компоненты

```
mobile (Flutter) ──┐
                   ├──HTTPS/JSON──> backend (ASP.NET Core 10) ──EF Core──> PostgreSQL
admin (React)   ───┘
```

Вся бизнес-логика и проверка прав находятся в backend. Мобильное приложение и веб-панель только
отображают данные и отправляют команды. Логика не дублируется: например, статус абонемента всегда
вычисляет сервер (`effectiveStatus`).

### Мобильное приложение: `mobile/lib`

| Папка | Назначение |
|---|---|

| `state/` | Сессия (`SessionController`) и язык (`LocaleController`) |

После входа приложение выбирает интерфейс по роли: `Client` — приложение клиента, `Trainer` —
кабинет тренера. Администраторы работают только в веб-панели.

### Веб-панель: `admin/src`

`api/` — HTTP-клиент и типы, `auth/` — сессия, `pages/` — страницы, `components/` — общие элементы
интерфейса, `lib/` — форматирование и хуки.

## Модель данных

| Сущность | Ключевые поля и правила |
|---|---|
| `Role` | Admin / Trainer / Client (сидируются миграцией). У пользователя одна роль |
| `User` | Телефон в формате E.164 (уникальный), PBKDF2-хеш пароля, статус Active/Blocked/Deleted, `DeletedAt`, флаг `MustChangePassword`, счётчик неудачных входов, блокировка по времени |
| `RefreshToken` | Хранится только SHA-256 хеш. Ротация, цепочка `ReplacedByTokenId` |
| `PhoneVerificationCode` | Хеш кода, срок 5 минут, не более 5 попыток (подготовка к этапу 2) |
| `ClientProfile` | 1:1 с `User`, закреплённый тренер (`AssignedTrainerId`), служебные заметки (видны только администратору), флаг `WithoutTrainer` — клиент выбрал «Без тренера» (снимается, когда тренер назначен), `AccessNo` — номер человека на терминалах (уникальный, из последовательности `ClientAccessNumbers` с 1001, выдаётся с первым фото лица) |
| `TrainerProfile` | 1:1 с `User`, специализация, опыт, флаги «набирает клиентов» и «активен», `Telegram` и `Instagram` (только ник, без «@») |
| `MembershipPlan` | Unlimited или LimitedVisits, срок в днях, лимит посещений, цена (справочно). CHECK-ограничения |
| `Membership` | Клиент, план, `StartDate` и `EndDate` (даты клуба, конец включительно), статус Active/Frozen/Cancelled, снимок лимита посещений, `xmin` для конкурентного доступа |
| `TrainerRequest` | Pending/Accepted/Rejected/Cancelled. Частичный уникальный индекс: одна ожидающая заявка на пару «клиент — тренер» |
| `TrainingSession` | Тренер, клиент, начало (UTC), длительность 15–480 минут, статус |
| `MembershipFreeze` | Период заморозки абонемента (даты клуба, включительно). При создании `EndDate` абонемента и последующих абонементов клиента сдвигаются на длину заморозки, при досрочной разморозке — обратно на неиспользованные дни. Текущей или запланированной может быть только одна. Каждая строка считается в лимит заморозок; отменённая до начала заморозка удаляется и не считается |
| `MembershipRequest` | Заявка клиента из приложения: New / Renew / Change, план, статус Pending/Completed/Rejected/Cancelled, назначенный абонемент. Не больше одной ожидающей заявки на клиента (частичный уникальный индекс) |
| `Visit` | Клиент, абонемент, время, источник: `Manual` (администратор), `QrScan` (QR-пропуск на ресепшене) или `FaceTerminal` (проход через терминал по лицу) |
| `Notification` | Тип, связанный объект, `Payload`. Текст локализует клиентское приложение |
| `Banner` | Баннер главного экрана приложения: заголовок, описание, `IsActive`, порядок `SortOrder` |
| `BannerMedia` | Фото (JPEG/PNG/WebP) или видео (MP4/MOV) баннера, порядок в галерее. Первое фото — обложка. Сам файл лежит в `MediaStorage` (папка `Media:RootPath`), в базе только тип и размер; удаляется каскадом вместе с баннером |

| `ClientFace` | Фото лица клиента для терминалов: JPEG до 200 КБ, номер версии (растёт при замене), кто и когда загрузил, время согласия. 1:1 с `ClientProfile`, байты отдельно от профиля |
| `AccessDevice` | Терминал распознавания лиц: адрес, логин, пароль (зашифрован AES-256-GCM, как секреты интеграций), «на вход — отмечать посещения», номер двери, секретный токен адреса событий, модель/серийный номер/прошивка, последняя связь и ошибка |
| `AccessDeviceUser` | Что терминал подтвердил по клиенту: номер, записанные имя и период (`AccessKey`), версия фото, состояние Pending/Synced/Failed/PhotoRejected, ошибка, повтор после паузы |
| `AccessEvent` | Журнал проходов и отказов от терминалов: время, терминал, номер и клиент, разрешён ли проход, код события, посещение или причина, почему оно не записано. Повторная доставка отсекается уникальным индексом по номеру события устройства |

У всех сущностей есть `Id` (UUID v7), `CreatedAt` и `UpdatedAt`; временные метки выставляет `AppDbContext`.
Внешние ключи настроены с `Restrict`, поэтому каскадного удаления бизнес-данных нет. Исключение — служебные
данные входа по лицу: фото и состояние синхронизации удаляются вместе с клиентом или терминалом (`Cascade`),
а записи журнала проходов при удалении терминала остаются (`SetNull`, имя терминала сохранено в записи).

## Бизнес-правила

- **Статус абонемента** вычисляется по дате клуба (Asia/Tashkent) в `MembershipStatusCalculator`.
  Порядок проверок: Cancelled → Expired (дата позже `EndDate`) → Frozen → Upcoming → Exhausted
  (лимит посещений) → Active. Истёкший абонемент никогда не считается активным.
- **Назначение абонемента**: `EndDate = StartDate + DurationDays − 1`. Пересечение с другим
  неотменённым абонементом клиента запрещено. Гонку исключает блокировка строки клиента
  (`SELECT … FOR UPDATE`). Изменения плана не затрагивают уже выданные абонементы.
- **Заявка на тренера**: тренер должен быть активен и набирать клиентов. Повторная ожидающая
  заявка запрещена дважды: проверкой в коде и уникальным индексом в БД (параллельные запросы →
  409). При принятии клиент закрепляется за тренером, а остальные ожидающие заявки клиента
  автоматически отменяются.
- **Тренировки**: тренер назначает их только своим клиентам и только на будущее время. Пересечение
  с другими тренировками тренера запрещено. Провести можно только начавшуюся тренировку; изменить
  можно только запланированную.
  - Клиент: `GET /api/me/training-sessions?scope=Upcoming` — запланированные и ещё не закончившиеся,
    ближайшие первыми; `scope=History` — закончившиеся, проведённые и отменённые, свежие первыми
    (постранично). Тренировка, которая уже идёт, остаётся в предстоящих.
  - Тренер: `GET /api/trainer/sessions` по умолчанию возвращает период «7 дней назад — 30 дней вперёд»,
    чтобы неотмеченные прошедшие тренировки можно было провести или отменить. В приложении они помечены
    «Прошла» и «Нажмите, чтобы отметить результат».
  - Отсутствие действующего абонемента тренировки не блокирует: клиент видит предупреждение, тренер —
    предупреждение при создании. Нужно ли это ограничение, ещё предстоит согласовать (см. PROGRESS.md).
- **Актуальность данных в приложении**: вкладки перезагружают данные при каждом переключении, экраны
  с `AsyncView` — при возврате приложения из фона, плюс pull-to-refresh.
- **Посещение** (вводит администратор) привязывается к абонементу, действующему в этот день. Без
  действующего абонемента или при исчерпанном лимите → 409.
- **Часовой пояс**: в БД хранятся даты (`date`) и моменты в UTC. «Сегодня» вычисляет `IClubClock`
  (`Club:TimeZoneId`). Веб-панель и приложение показывают время клуба.

## Безопасность

- **Аутентификация**: телефон и пароль. Хеширование — `PasswordHasher<T>` из ASP.NET Identity
  (PBKDF2). Access-токен JWT живёт 15 минут. Refresh-токен действует 30 дней с ротацией: повторное
  использование уже ротированного токена отзывает все сессии пользователя.
- **Временные пароли**: если пароль задал персонал (клиент или тренер создан администратором, пароль
  сброшен, первый администратор из конфигурации), у пользователя ставится `MustChangePassword`. Пока
  флаг стоит, `PasswordChangeGate` отвечает `403 password_change_required` на всё, кроме `/api/auth/me`,
  `change-password` и `logout`. Мобильное приложение и веб-панель в этом случае показывают только экран
  смены пароля. `change-password` снимает флаг, завершает остальные сессии и выдаёт новую пару токенов.
- **Защита входа**: блокировка на 15 минут после 5 неудачных попыток, rate limiting `/api/auth/*`
  по IP, одинаковая ошибка для неизвестного номера и неверного пароля.
- **Авторизация** только на сервере: `[Authorize(Roles = ...)]` на каждом контроллере. При каждом
  запросе проверяется, что пользователь активен и роль не изменилась, поэтому блокировка действует
  сразу.
- **Изоляция данных**: id клиента или тренера берётся из токена, а не из запроса. Чужие объекты
  для тренера и клиента возвращают 404 — существование не раскрывается. Тренер не видит служебных
  заметок. Телефон тренера клиенту не показывается; Telegram и Instagram в общем списке тренеров не
  отдаются — клиент получает их в ответе на свою заявку (`TrainerRequestDto`) и у своего закреплённого тренера.
- **Файлы баннеров** (`GET /api/banners/media/{id}.{ext}`) отдаются без токена, как фото тренеров: id случайные,
  содержимое — реклама клуба. Формат проверяется по содержимому файла, размер ограничен (фото 10 МБ, видео 100 МБ).
- **Фото лиц** (биометрия) отдаются только по токену: клиенту — его собственное (`/api/me/face/photo`), администратору —
  из карточки клиента, с `Cache-Control: private, no-store`. Загрузка без согласия отклоняется (`face_consent_required`).
  Пароли терминалов шифруются тем же ключом, что и секреты интеграций, и никогда не возвращаются API.
  Адрес приёма событий открыт без токена: устройство не умеет авторизоваться. Его защищает случайный токен
  устройства длиной 32 символа. Неизвестный токен получает ответ 404.
- **Секреты**: только через переменные окружения или `dotnet user-secrets`. В `appsettings.json`
  секретов нет; без `Jwt:SigningKey` (не короче 32 символов) и строки подключения API не запускается.
- **Логи** не содержат паролей, токенов и SMS-кодов (кроме явно помеченного Development-отправителя, см. ниже).
- **Хранение токенов**: в мобильном приложении — Keychain/Keystore (`flutter_secure_storage`).
  В веб-панели access-токен хранится в памяти, refresh-токен — в `sessionStorage` и удаляется при закрытии вкладки.
- **HTTP без TLS** разрешён только для разработки: Android — `usesCleartextTraffic` в debug-манифесте,
  iOS — `NSAllowsLocalNetworking`. В Production нужен HTTPS за обратным прокси.

## Ресепшен: QR-пропуск, заморозка, продление

- **QR-пропуск** (`PassTokenService`): `FF1` + Base32(id клиента, срок, HMAC-SHA256 в усечении до 80 бит). Ключ
  выводится из `Jwt:SigningKey`, отдельный секрет не нужен. Новый код каждые 30 секунд, каждый действует 60 секунд:
  скриншот или пересланный код перестаёт работать через минуту. Только A–Z и 0–9: компактный QR и одинаковый ввод
  сканером в любой раскладке (панель читает клавиши по физическому положению).
- **Проход** (`POST /api/admin/check-in`, `CheckInService`): проверка подписи и срока, блокировки клиента и
  абонемента на сегодня. Разрешено → создаётся `Visit` (`QrScan`) под блокировкой строки клиента, так что двойной
  скан не создаёт двух визитов и не превышает лимит; повтор в течение 2 минут возвращает тот же визит. Отказ —
  обычный ответ с причиной (`no_membership`, `membership_expired`, `membership_frozen`, `visit_limit_reached`, …).
  Ошибочный вход отменяется в течение 15 минут (`DELETE /api/admin/visits/{id}`, запись в журнал аудита).
- **Заморозка** — клиент сам в приложении (`POST /api/me/memberships/{id}/freeze`, `/unfreeze`) или администратор
  (`POST /api/admin/memberships/{id}/freeze`, `/unfreeze`), правила одинаковые (`MembershipService`):
  только планы от 6 месяцев (`MinFreezePlanDays` = 180 дней), 3 заморозки на каждый начатый год срока плана
  (`FreezesAllowed`: 180–365 дней — 3, 366–730 — 6), одна заморозка — от 1 до 30 дней (`MaxFreezeDays`). Остаток
  заморозок приходит в `MembershipDto` (`FreezesAllowed`, `FreezesUsed`). Уведомление клиенту отправляется, только
  если заморозил администратор. См. `MembershipFreeze`.
- **Продление**: клиент отправляет `MembershipRequest`, администратор принимает оплату на ресепшене и оформляет
  заявку (`/api/admin/membership-requests/{id}/complete`): по умолчанию новый абонемент начинается на следующий день
  после последнего. Кнопки «Сменить тариф» в приложении нет; API по-прежнему принимает вид `Change` (старые заявки).

## Баннеры главного экрана

- Администратор ведёт баннеры в разделе «Баннеры» веб-панели (`/api/admin/banners`): заголовок, описание, показ в
  приложении, порядок; фото и видео загружаются по одному файлу (`POST /api/admin/banners/{id}/media`), сразу
  сохраняются, их порядок меняется (`PUT .../media/order`), первое фото — обложка.
- Приложение запрашивает `GET /api/banners` (только включённые) и показывает карусель под приветствием. Нажатие
  открывает экран с галереей фото и видео (видео проигрывается потоково, сервер поддерживает Range-запросы),
  заголовком и описанием. Если баннеры не загрузились, главный экран показывается без них.
- Файлы хранит `MediaStorage` на диске (`Media:RootPath`, по умолчанию `App_Data/media` рядом с API, в Docker —
  volume `media-data`), а не в PostgreSQL: видео слишком велики для базы.

## Выбор тренера

- Клиент может выбрать «Заниматься без тренера» (`POST /api/me/without-trainer`): ожидающие заявки тренерам
  отменяются, приложение перестаёт предлагать выбрать тренера, а кнопка «Начать тренировку» открывает QR-пропуск.
  Выбрать тренера можно в любой момент; флаг снимается, когда тренер принимает заявку или его назначает администратор.
- После отправки заявки тренеру приложение показывает экран «Заявка отправлена» с Telegram и Instagram тренера
  (если они заполнены в карточке тренера в веб-панели).

## Вход по лицу: терминалы Hikvision

Поддерживаются терминалы распознавания лиц Hikvision серии MinMoe по протоколу ISAPI, в первую очередь
DS-K1T343MFWX. Терминал сам управляет турникетом (реле или Wiegand) и сам решает, пускать ли человека.
Сервер записывает на терминал, кого и в какие дни пускать.

- **Фото**. Клиент добавляет фото в приложении: селфи или фото из галереи, с обязательным согласием на обработку.
  Сделать это можно в любой момент, а приложение отдельно предлагает добавить фото после заявки на абонемент
  и на главном экране. Администратор может загрузить фото в карточке клиента, если клиент дал согласие на ресепшене.
  Фото принимаются только в формате JPEG, до 200 КБ (ограничение терминала), от 240 до 4096 пикселей по каждой стороне.
  Приложение и веб-панель сами уменьшают и сжимают снимок. Фото — биометрические персональные данные:
  без авторизации они не отдаются, клиент видит только своё, а удаление фото убирает клиента с терминалов.
  Загрузку и удаление фиксирует журнал аудита.
- **Период доступа**. `AccessWindowCalculator` берёт дни абонементов клиента и вычитает из них заморозки.
  Абонементы, идущие подряд, склеиваются. Из результата выбирается первый непрерывный отрезок, который
  заканчивается сегодня или позже. На терминал он пишется как срок действия человека
  (`Valid.beginTime/endTime` в местном времени терминала). Поэтому окончание абонемента или начало заморозки
  срабатывают на терминале сами, даже без связи с сервером. Клиент без такого отрезка удаляется с терминала:
  абонемент истёк, отменён, заморожен администратором бессрочно, израсходованы посещения или клиент заблокирован.
- **Синхронизация** (`AccessSyncService`). Сервер сравнивает план с тем, что терминал подтвердил в прошлый раз
  (`AccessDeviceUser`), и отправляет только разницу. Сначала идут удаления, затем добавления и изменения, не
  больше 100 операций за проход. Синхронизацию запускает фоновый `AccessSyncWorker`: через 2 секунды после
  изменения абонемента, заморозки, посещения, фото, имени или блокировки клиента (их ловит
  `AccessChangeInterceptor` на сохранении в EF) и в любом случае раз в минуту. Ещё её можно запустить кнопкой
  в веб-панели. При ошибке по одному клиенту запись повторяется через 1, 5, 15 и 60 минут. Если терминал
  недоступен или не принимает пароль, проход останавливается, а ошибка видна в веб-панели. Если терминал
  не нашёл лицо на фото, это фото больше не отправляется: клиент видит в приложении просьбу сделать новое.
- **Вызовы ISAPI** (`HikvisionTerminal`, Digest-аутентификация):
  - человек: `UserInfo/Search`, затем `UserInfo/Record` или `UserInfo/Modify`; удаление — `UserInfo/Delete`, а на новых прошивках — `UserInfoDetail/Delete`;
  - лицо: `FDLib/FDSetUp` в библиотеке 1 (`blackFD`), а на старых прошивках — удаление через
    `FDSearch/Delete` и загрузка через `FaceDataRecord`;
  - проверка связи: `System/deviceInfo` и `System/time`.

  Номер человека на терминале — `ClientProfile.AccessNo`, имя обрезается до 32 байт.
- **События**. Терминал отправляет события на адрес `POST /api/access/hikvision/events/{token}` (HTTP Listening).
  Подписать запрос терминал не может, поэтому в адресе стоит случайный токен устройства. Проход (код 75 — лицо,
  38 — отпечаток, 1 — карта) с терминала «на вход» записывает посещение (`VisitSource.FaceTerminal`)
  по тем же правилам, что и QR-пропуск. Повторный проход в течение 2 минут не создаёт новое посещение.
  Если на сервере у клиента нет действующего абонемента, а терминал пропустил (не успел обновиться),
  посещение не записывается, проход попадает в журнал с причиной и в лог как предупреждение.
  Отказы известного человека тоже пишутся в журнал. Остальные события только отмечают, что терминал на связи.
- **Права**. Терминалами (адреса и пароли) управляет администратор с правом интеграций. Журнал проходов
  и фото клиентов доступны всем администраторам.
- **Ограничения**. Вызовы ISAPI сделаны по открытой документации и проверены на эмуляторе. На реальном
  DS-K1T343MFWX их нужно проверить при подключении (OPERATIONS.md, раздел 7). Нужна сетевая доступность
  терминала с сервера (одна локальная сеть или VPN). Облачные Hik-Connect и ISUP не используются.

## Удаление аккаунта

App Store (правило 5.1.1(v)) и Google Play требуют, чтобы зарегистрированный в приложении клиент мог удалить
аккаунт сам. `AccountDeletionService`:
- **Кто удаляет.** Клиент в приложении: «Профиль» → «Удалить аккаунт», с паролем (`POST /api/me/delete-account`).
  Или администратор по просьбе клиента: карточка клиента → «Удалить аккаунт» (`POST /api/admin/clients/{id}/delete`).
  Просьбы приходят через страницу `/legal/delete-account`, на неё ссылается Google Play.
- **Что стирается.** Имя (становится «Удалённый клиент»), телефон (заменяется заглушкой `del-…`, номер можно
  зарегистрировать заново), e-mail, дата рождения, пол, заметки администратора. Ещё удаляются фото лица (терминалы
  забывают человека при следующей синхронизации), уведомления и комментарии в заявках тренерам. Снимается
  закреплённый тренер. Отменяются заявки на рассмотрении, будущие тренировки, текущие и будущие абонементы. Все
  сессии завершаются, пароль больше ни к чему не подходит. В записях журнала аудита о клиенте имя и телефон
  заменяются на «—».
- **Что остаётся.** Абонементы, посещения, заморозки и прошедшие тренировки остаются, но без персональных данных:
  они нужны клубу для учёта. Отчёты считают абонементы по дате продажи, поэтому отмена при удалении их не меняет.
- **Последствия.** Статус `Deleted` окончательный: изменить такого клиента, сбросить ему пароль, назначить
  абонемент или загрузить фото нельзя (`409 client_deleted`). В списке клиентов удалённые видны только с фильтром
  «Удалённые», в счётчик клиентов на главной они не входят.

## Питание и ИИ

Раздел «Питание» описан в [NUTRITION.md](NUTRITION.md). Главное: ИИ только распознаёт блюдо и ингредиенты с
весом, а калории и БЖУ считает сервер по базе продуктов (USDA, Open Food Facts, этикетки); ответ ИИ проверяется по
схеме; ИИ-провайдер заменяем; ИИ-функции требуют отдельного согласия клиента; в дневник блюдо попадает только по
подтверждению клиента. При удалении аккаунта данные питания и фото еды удаляются полностью.
