# Эксплуатация: конфигурация, секреты, миграции, резервное копирование

Документ для того, кто разворачивает систему на сервере клуба. Боевой сервер в рамках этапа 1 не
настраивался; ниже — требования и проверенные локально процедуры.

## 1. Окружения

| Окружение | Где используется | Особенности |
|---|---|---|
| `Development` | компьютер разработчика | Swagger, SMS-код в лог, короткие dev-логины `1`/`2`/`3`, секреты из user-secrets |
| `Testing` | `dotnet test` | одноразовый PostgreSQL в контейнере; dev-механизмов нет |
| `Production` | сервер клуба | dev-механизмов нет; Swagger закрыт; HSTS; секреты только из переменных окружения |

`Production` — значение по умолчанию для compose-профиля `api` (`API_ENVIRONMENT=Production`).
**Никогда не запускайте боевой API с `ASPNETCORE_ENVIRONMENT=Development`.**

## 2. Секреты

| Секрет | Откуда берётся | Проверка |
|---|---|---|
| Пароль PostgreSQL | `POSTGRES_PASSWORD` в `infrastructure/.env` (не в git), далее в `ConnectionStrings__Default` | compose не стартует без него |
| Ключ подписи JWT | `Jwt__SigningKey` (`JWT_SIGNING_KEY` в `.env`), не короче 32 символов: `openssl rand -base64 48` | API **не запускается** без ключа (проверено) |
| Первый администратор | `Bootstrap__AdminPhone`, `Bootstrap__AdminPassword` | пароль временный: при первом входе обязательна смена (проверено) |
| Ключ API ИИ-сервиса | `Ai__ApiKey` (`AI_API_KEY` в `.env`) вместе с `Ai__Provider=Anthropic` | необязателен: без него анализ фото еды выключен (`ai_not_configured`), дневник и штрихкоды работают. Расходы — в таблице `AiUsage` и в логе, месячный предел `Ai__MonthlyBudgetUsd` ([NUTRITION.md](NUTRITION.md)) |
| Ключ шифрования секретов интеграций | `Integrations__EncryptionKey` (`INTEGRATIONS_ENCRYPTION_KEY` в `.env`), 32 байта в base64: `openssl rand -base64 32` | необязателен: без него API работает, но секреты Click/Payme сохранить нельзя (ответ `encryption_not_configured`); неверный формат — API не запускается |

- В репозитории секретов нет: `appsettings.json` содержит пустые значения, `.env` в `.gitignore`.
- В логах API нет паролей и токенов (проверено поиском значений в логе Production-запуска).
- После первого входа администратора уберите `BOOTSTRAP_ADMIN_PASSWORD` из `.env`: повторно он не используется.
- Ключ JWT меняется заменой `Jwt__SigningKey` и перезапуском; все пользователи войдут заново.
- Секреты Click/Payme хранятся в PostgreSQL только зашифрованными (AES-256-GCM, таблица `IntegrationSecrets`); API их не возвращает, в журнал аудита и логи пишутся только имена полей. Ключ шифрования держите неизменным и в резервной копии отдельно от базы: при его смене или потере сохранённые секреты нужно ввести заново.
- Настройки интеграций видит и меняет только администратор с правом `CanManageIntegrations`. Его получает первый администратор (Bootstrap и миграция `AddIntegrationSettings`); выдать право другому пока можно только запросом в БД.

## 3. Миграции базы данных

Миграции EF Core лежат в `backend/src/FitnessFormulasi.Api/Data/Migrations`:
`20261023180145_InitialCreate`, `20261023213010_AddMustChangePassword`.

- Автоприменение при старте: `Database__MigrateOnStartup=true` (включено в compose-профиле `api`).
- Ручное применение (из исходников, с доступом к базе):
  `cd backend/src/FitnessFormulasi.Api && ConnectionStrings__Default="…" dotnet ef database update`
- SQL-скрипт для ревью до применения:
  `dotnet ef migrations script --idempotent -o migrate.sql`
- Расхождений модели и миграций нет: `dotnet ef migrations has-pending-model-changes` →
  «No changes have been made to the model since the last migration».
- **Перед применением новых миграций на боевой базе — резервная копия (раздел 4).**

## 4. Резервное копирование и восстановление

Процедура проверена 24.10.2026 на временной базе (`infrastructure/scripts/production-smoke.sh`, шаг 3):
дамп снят, восстановлен в новую базу, число записей совпало.

### Создание копии

```bash
# Формат custom (-Fc): сжатый, позволяет восстанавливать выборочно.
docker compose -f infrastructure/docker-compose.yml exec -T postgres \
  pg_dump -U ff_app -d fitness_formulasi -Fc > backup/ff_$(date +%Y%m%d_%H%M).dump
```

Фото и видео баннеров и фото еды из раздела «Питание» хранятся не в базе, а в папке `Media:RootPath` (в compose — volume `media-data`,
путь `/data/media` в контейнере). Копируйте её вместе с дампом, иначе после восстановления баннеры останутся без файлов:

```bash
docker run --rm -v fitness-formulasi_media-data:/data/media -v "$PWD/backup":/backup alpine \
  tar czf /backup/ff_media_$(date +%Y%m%d_%H%M).tgz -C /data media
```

Рекомендуемый порядок для клуба (согласовать с заказчиком):
- ежедневная копия по расписанию (cron) и хранение не менее 14 последних;
- копия перед каждым обновлением системы;
- хранение копий **вне** сервера базы (другой диск или облачное хранилище);
- ежемесячная проверка восстановления в отдельную базу.

### Восстановление

Восстанавливайте **в новую базу**, проверяйте и только потом переключайте API. Не восстанавливайте
поверх рабочей базы и не удаляйте Docker volume `postgres-data`.

```bash
docker compose -f infrastructure/docker-compose.yml exec -T postgres createdb -U ff_app ff_restore
docker compose -f infrastructure/docker-compose.yml exec -T postgres \
  pg_restore -U ff_app -d ff_restore --no-owner < backup/ff_YYYYMMDD_HHMM.dump
# Проверка: число записей в основных таблицах
docker compose -f infrastructure/docker-compose.yml exec -T postgres \
  psql -U ff_app -d ff_restore -c 'select count(*) from "Users"' -c 'select count(*) from "Memberships"'
```

Переключение: указать `Database=ff_restore` в `ConnectionStrings__Default` и перезапустить API.

## 5. Требования к боевому развёртыванию (не выполнялось в этапе 1)

| Требование | Почему | Статус |
|---|---|---|
| HTTPS через обратный прокси (nginx, Caddy и т.п.) с сертификатом | API слушает HTTP; HSTS отправляется только по HTTPS | на стороне сервера заказчика |
| Настроить передачу IP клиента от прокси (`ForwardedHeaders`) | Ограничение 20 входов в минуту считается по IP. За прокси все клиенты будут иметь IP прокси и делить один лимит | **требует доработки до запуска**: в коде API обработка `X-Forwarded-For` не включена |
| Мобильное приложение собирать с адресом API: `mobile/scripts/build_release.sh https://api…` (AAB для Google Play и IPA для App Store) | без адреса release-сборка обращается к `127.0.0.1`/`10.0.2.2` и не работает | обязательный шаг сборки, [STORE.md](STORE.md), раздел 4 |
| Обратный прокси пропускает `/legal/` к API, реквизиты `Legal__*` заполнены | на страницы политики и удаления аккаунта ссылаются App Store и Google Play | до отправки в магазины |
| Веб-панель: `VITE_API_URL=https://api… npm run build`, `Cors__AllowedOrigins__0` = адрес панели | иначе браузер заблокирует запросы | обязательный шаг сборки |
| Боевую базу создавать с нуля, а не копией dev-базы | в dev-базе есть тестовые записи «E2E» и dev-аккаунты `+99800000000x` | проверка: `select count(*) from "Users" where "Phone" like '+99800000000%'` → 0 |
| Порт PostgreSQL не публиковать наружу | в compose привязан к `127.0.0.1` | выполнено в compose |
| Обратный прокси пропускает загрузку файлов до 100 МБ (nginx: `client_max_body_size 110m;` для `/api/admin/banners/`) | видео баннеров до 100 МБ; по умолчанию nginx режет тело запроса больше 1 МБ | на стороне сервера заказчика |
| Постоянное хранилище для `Media:RootPath` и его резервное копирование (раздел 4) | там лежат фото и видео баннеров | в compose — volume `media-data` |
| Публикация в App Store / Google Play | нужны аккаунты разработчика заказчика | не входит в п. 2.1 договора, согласовать отдельно. Порядок, тексты и ответы для консолей — [STORE.md](STORE.md) |

## 6. Проверка Production-режима без боевого сервера

```bash
cd backend && dotnet publish src/FitnessFormulasi.Api -c Release -o /tmp/ff-check/publish
zsh infrastructure/scripts/production-smoke.sh /tmp/ff-check
```

Скрипт поднимает временный PostgreSQL без постоянного тома (порт `127.0.0.1:55432`), запускает release-сборку
API в `Production` со случайными одноразовыми секретами (порт `5091`), проверяет запуск без ключа,
миграции, отсутствие dev-аккаунтов и dev-логинов, закрытый Swagger, обязательную смену пароля
администратора, отсутствие секретов в логе, затем резервное копирование и восстановление и удаляет
временный контейнер. Существующие базы и контейнеры не затрагиваются.

## 7. Подключение терминала распознавания лиц Hikvision (DS-K1T343MFWX)

Как это устроено, описано в ARCHITECTURE.md, раздел «Вход по лицу». Код протестирован на эмуляторе ISAPI.
**На реальном терминале его ещё никто не проверял**: пройдите проверку из п. 7.5 при первом подключении.

### 7.1. Сеть

- API обращается к терминалу по HTTP (ISAPI, Digest-аутентификация). Терминал отправляет события на API.
  Нужна связь в обе стороны: сервер и терминал в одной сети клуба или соединены VPN (например, WireGuard),
  если API работает в облаке. Облачные Hik-Connect и ISUP не используются.
- **Не открывайте веб-интерфейс терминала в интернет** (проброс портов). Дайте терминалу постоянный IP-адрес.
- API в Docker обращается к адресам локальной сети через сеть Docker; отдельная настройка не нужна.

### 7.2. Подготовка терминала (веб-интерфейс терминала)

1. Активируйте устройство и задайте надёжный пароль учётной записи `admin`.
2. **Обновите прошивку**: прошивки DS-K1T343MFWX до V3.14.0_build230117 включительно содержат уязвимость
   CVE-2023-28810.
3. Время: включите NTP и часовой пояс клуба (UTC+05:00, Ташкент). Сроки доступа записываются по местному
   времени терминала. «Проверить связь» в веб-панели предупредит, если часовой пояс или время расходятся.
4. Режим аутентификации — по лицу (или «лицо или карта»), выход реле — на турникет.

### 7.3. Настройка в веб-панели

1. Задайте ключ шифрования `Integrations__EncryptionKey` (раздел 2), иначе пароль терминала не сохранится.
2. «Турникеты» → «Добавить» (раздел виден администратору с правом интеграций): название, IP-адрес, логин
   и пароль терминала, номер двери (1 для турникета на одну дверь), «Терминал на вход — отмечать посещения».
   Терминал на выход добавляйте без этой галочки.
3. Нажмите «Проверить связь»: должны отобразиться модель, серийный номер и прошивка.
4. Нажмите «Синхронизировать»: на терминал попадут клиенты, у которых есть фото и действующий или
   ближайший абонемент. Дальше синхронизация идёт сама: через несколько секунд после изменений и раз в минуту.

### 7.4. Приём событий (проходы → посещения)

В веб-интерфейсе терминала откройте Configuration → Network → Advanced Settings → HTTP Listening
(в некоторых прошивках — Event → Alarm Server). Укажите:

- адрес сервера API (IP или домен) и порт;
- URL — путь из веб-панели («Адрес для событий» у терминала);
- протокол HTTP, формат JSON.

Путь содержит секретный токен терминала: не публикуйте его. Сделайте тестовый проход: он появится в журнале
на странице «Турникеты», а посещение — в разделе «Посещения» с источником «Турникет».

Если события идут через обратный прокси, разрешите на этом пути тело запроса до 5 МБ, потому что события
приходят с кадром с камеры. Для nginx: `client_max_body_size 5m;` для `/api/access/hikvision/`.

### 7.5. Проверка на реальном терминале (при первом подключении)

| Шаг | Ожидаемый результат |
|---|---|
| «Проверить связь» | Модель DS-K1T343MFWX, прошивка новее V3.14.0, предупреждений о времени нет |
| Клиент с абонементом добавляет фото в приложении | Через минуту статус «Готово»; в веб-интерфейсе терминала (Person Management) есть человек с номером из карточки клиента, сроком действия абонемента и фото |
| Проход клиента | Турникет открывается; запись в журнале «Турникеты»; посещение «Турникет» в карточке клиента |
| Заморозка абонемента | Срок действия на терминале заканчивается накануне заморозки; во время заморозки терминал не пускает |
| Абонемент закончился или клиент удалил фото | Человек удалён с терминала в течение минуты |
| Фото без лица (например, фото стены) | В приложении «Терминал не распознал лицо», у администратора причина в списке проблем терминала |

Если запись на терминал не проходит, текст ответа устройства виден у терминала в веб-панели (последняя ошибка
и список проблем). Скорее всего, прошивка отвечает иначе, чем описано в документации ISAPI. С этим текстом
нужно доработать `Features/Access/HikvisionTerminal.cs`.

### 7.6. Ёмкость, хранение и персональные данные

- DS-K1T343MFWX хранит около 1 500 лиц (точное число смотрите в паспорте вашего исполнения). На терминале
  только клиенты с фото и действующим или ближайшим абонементом; остальные удаляются автоматически.
- Фото лиц хранятся в PostgreSQL (таблица `ClientFaces`) и попадают в резервную копию базы. Копии
  содержат биометрические данные: храните их зашифрованными и с ограниченным доступом.
- Фото принимаются только с согласием клиента (время согласия хранится, загрузка и удаление попадают
  в журнал аудита). Клиент может удалить фото в приложении. Требования закона Республики Узбекистан
  «О персональных данных» к биометрическим данным и к хранению данных граждан на серверах в Узбекистане
  согласуйте с юристом клуба до запуска.
