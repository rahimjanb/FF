# Тестирование

## Автоматические тесты

| Команда | Что проверяет |
|---|---|
| `cd backend && dotnet test` | 79 тестов. Интеграционные тесты идут на **реальном PostgreSQL** в одноразовом контейнере (Testcontainers, нужен запущенный Docker) |
| `cd mobile && flutter analyze && flutter test` | Статический анализ и 37 тестов: валидаторы, разбор моделей, API-клиент (обновление токена, ошибки), сквозной сценарий UI с тестовым HTTP-backend, обязательная смена временного пароля, экраны тренировок клиента и тренера, отметка тренировки, кнопка «Назад» (`test/workouts_test.dart`), подгрузка страниц (`test/pagination_test.dart`) |
| `cd admin && npm run lint && npm run build` | Проверка oxlint и TypeScript, production-сборка |
| `cd admin && ADMIN_PHONE=… ADMIN_PASSWORD=… npm run test:e2e` | Playwright в установленном Google Chrome против **живого API** (нужны запущенные API и PostgreSQL): 5 тестов — приоритетный сценарий и операции администратора, см. ниже |

Покрытие backend-тестами:
- **Регистрация и вход**: хеширование пароля, дубли номера, валидация, одинаковая ошибка для неизвестного номера и неверного пароля, блокировка после 5 попыток, ротация refresh-токена и обнаружение его повторного использования, logout, немедленная блокировка доступа, просроченный JWT, 503 для SMS без провайдера, `/health`.
- **Роли и доступ**: анонимные запросы → 401; клиент → admin/trainer endpoints → 403; тренер → admin/client endpoints → 403; тренер не видит и не может назначить тренировку чужим клиентам; клиент не может отменить чужую заявку; клиент не видит служебных заметок и телефонов тренеров.
- **Абонементы**: дата окончания включительно, запрет пересечений, истёкший абонемент не считается активным, смена дня по времени Ташкента, заморозка и отмена, неактивный план нельзя назначить, лимит посещений.
- **Заявки**: создание, дубли (включая 5 параллельных запросов), отмена и повторная заявка, принятие с закреплением клиента и автоотменой других заявок, отклонение с уведомлением, обработка администратором, тренер, который не набирает клиентов.
- **Тренировки**: создание, запрет пересечений и времени в прошлом, отображение у клиента, отмена.
- **Временные пароли**: клиент и тренер, созданные администратором, получают `403 password_change_required` до смены пароля; нельзя задать тот же пароль; после смены старые сессии и временный пароль недействительны; сброс пароля администратором снова требует смены; у самостоятельно зарегистрированного клиента флага нет.
- **Тренировки** (`TrainingSessionTests.cs`): пустые списки; разделение на предстоящие и историю по времени и статусу (включая идущую и неотмеченную прошедшую); клиент видит только свои, тренер — только своё расписание; чужой тренер не может отменить или провести тренировку (404), клиент не имеет доступа к endpoints тренера (403); правила смены статуса; окно «7 дней назад»; проверка диапазона дат; после смены тренера прежний тренер не может назначать тренировки клиенту.
- **Списки администратора**: поиск по имени и телефону, пагинация, ограничение `pageSize` (не более 100), dashboard и отчёт.
- **Пагинация** (`PaginationTests.cs`): история тренировок клиента, уведомления и клиенты тренера проходятся по всем страницам маленьким `pageSize` при совпадающих ключах сортировки (одинаковое время начала, одинаковое `CreatedAt` у записей одной транзакции, одинаковые имена) — без пропусков и повторов, порядок сохраняется.
- **Профиль** (`ProfileTests.cs`): клиент меняет имя, e-mail, дату рождения и пол, но не телефон, роль и тренера; валидация полей; тренер редактирует свою карточку, клиенты видят изменения.
- **Проведённая тренировка** не создаёт посещение и не списывает абонемент (правило не утверждено).
- **Короткие dev-логины** вне `Development` отклоняются.

Flutter-тесты экранов тренировок (`test/workouts_test.dart`, данные из тестового HTTP-backend):
- **клиент**: тренер, предстоящие тренировки и история со статусами «Проведена», «Прошла», «Отменена»;
  пустое расписание без тренера и абонемента (подсказка, предупреждение, переход к выбору тренера);
  ошибка API → «Повторить» → данные; перезагрузка при возврате из фона;
- **тренер**: разделы «Предстоящие» и «Прошедшие за 7 дней», неотмеченная тренировка доступна для
  действий; пустое расписание и ошибка с повтором; перезагрузка при возврате из фона; предупреждение
  при создании тренировки для клиента без абонемента; после принятия заявки новый клиент появляется
  на вкладке «Клиенты».
- **действия с тренировкой**: «Отметить проведённой» у прошедшей → запрос к API, сообщение, список
  перезагружен, статус «Проведена», повторных действий нет; у будущей тренировки только «Отменить» с
  подтверждением («Не отменять» ничего не отправляет); ошибки `session_not_scheduled` (409) и `not_found`
  (404, например клиент перешёл к другому тренеру) показываются понятным текстом, список обновляется;
- **кнопка «Назад» Android** на другой вкладке возвращает на первую, а не закрывает приложение;
- **длинный список тренеров**: свой тренер и тренер с ожидающей заявкой показываются первыми.

Flutter-тесты подгрузки (`test/pagination_test.dart`): история тренировок клиента, уведомления и клиенты
тренера подгружаются кнопкой «Показать ещё» (страницы 20/30/30); при сдвиге страниц из-за новых записей
повторы отбрасываются; ошибка при подгрузке не теряет загруженное и повторяется; ожидающая заявка тренеру
видна, даже если за ней 40 более новых обработанных.

## Операции администратора в браузере (Playwright)

`admin/e2e/admin-operations.spec.ts`:
- **Тренеры**: повторный номер → понятная ошибка в форме; поиск; «Принимает новых клиентов» выключено →
  в списке «Закрыт», клиент получает `trainer_not_accepting`; сброс пароля → вход с новым временным
  паролем требует смены, старый не подходит; блокировка → `account_blocked` при входе.
- **Заявки**: отклонение с причиной, вкладки «Ожидает» / «Отклонена» / «Все», клиент видит статус и
  уведомление, повторная обработка → `request_not_pending`, тренер не закреплён.
- **Отчёты**: цифры на странице совпадают с API, растут после выдачи абонемента и посещения, за пустой
  период — нули и «Нет посещений за период».
- **Пагинация**: вторая страница тренеров содержит другие записи (до исправления возвращалась первая).

Запуск (все 5 тестов, один worker — тесты сравнивают итоги отчётов в общей базе):

```bash
cd admin && ADMIN_PHONE=1 ADMIN_PASSWORD=1 npm run test:e2e   # dev-администратор, см. DEVELOPMENT.md
```

Один прогон делает около 25 запросов к `/api/auth/*`, а API по умолчанию разрешает 20 в минуту с одного
IP. Для повторных локальных прогонов запускайте dev-API с повышенным лимитом только для этого процесса:
`RateLimiting__AuthPermitPerMinute=200 dotnet run …`. Значение по умолчанию и конфигурация не меняются.

## Приоритетный сценарий в браузере (Playwright)

`admin/e2e/priority-scenario.spec.ts`:
1. В панели администратор создаёт тренера, план и клиента с временным паролем, назначает абонемент и отмечает посещение.
2. Через API клиент входит с временным паролем, получает `password_change_required`, меняет пароль, видит абонемент и отправляет заявку тренеру; повторная заявка → 409.
3. В панели администратор принимает заявку, клиент видит назначенного тренера, у тренера в списке 1 клиент.

Каждый запуск создаёт новые записи с пометкой «E2E» и уникальными номерами. Существующие данные тест не изменяет.

## Сквозной тест мобильного приложения на реальном backend (симулятор или эмулятор)

Проверено 24.10.2026 на iOS-симуляторе iPhone 17 (iOS 27) и Android-эмуляторе `Medium_Phone_API_37.0`
(Android 17); приложение на эмуляторе обращается к API по `10.0.2.2:5080`.

Нужны запущенный API и две dev-учётные записи: клиент с абонементом и заявкой к тренеру, и сам тренер.

```bash
cd mobile
flutter test integration_test -d <device-id> \
  --dart-define=E2E_CLIENT_PHONE=+998... --dart-define=E2E_CLIENT_PASSWORD=... \
  --dart-define=E2E_TRAINER_PHONE=+998... --dart-define=E2E_TRAINER_PASSWORD=...
```

Если у учётной записи временный пароль, тест проходит экран обязательной смены и задаёт пароль из
`E2E_NEW_PASSWORD` (по умолчанию `MyOwn12345`).

Сценарий: клиент входит и видит активный абонемент → видит заявку или закреплённого тренера → выходит
→ тренер входит, принимает заявку → видит клиента в списке → создаёт тренировку на завтра через
«Расписание → Новая тренировка» → клиент входит и видит её на вкладке «Тренировки» вместе с тренером.

Для каждого запуска нужны свежие учётные записи: повторное создание тренировки на то же время у того же
тренера отклоняется как пересечение (`session_overlap`).

## Ручная проверка

1. **Веб-панель** (`http://localhost:5173`). Войдите как администратор → «Планы» → создайте план →
   «Клиенты» → «Новый клиент» → в карточке клиента «Назначить» абонемент → «Отметить посещение».
   На «Обзоре» счётчики изменятся.
2. **Тренер**. «Тренеры» → «Новый тренер» (телефон и временный пароль).
3. **Мобильное приложение, клиент**. Зарегистрируйтесь → «Тренеры» → откройте тренера → «Отправить заявку».
   Повторная заявка тому же тренеру не отправится.
4. **Мобильное приложение, тренер**. Войдите под тренером → «Заявки» → «Принять» → «Клиенты» →
   «Расписание» → «Новая тренировка».
5. **Клиент**. На главной видны абонемент, тренер и ближайшая тренировка; на вкладке «Профиль» можно
   изменить данные и переключить язык на O‘zbekcha.
6. **Swagger** (`/swagger`): кнопка Authorize, вставьте `accessToken` из `/api/auth/login`.

### Ручная проверка на Android-эмуляторе (24.10.2026)

- Клавиатура: у поля телефона цифровая клавиатура, форма поднимается над ней, поля не перекрываются;
  клавиша «далее» переводит на пароль, Enter отправляет форму.
- Навигация: «Назад» с регистрации возвращает на вход с сохранённым номером; «Назад» на вкладке
  «Тренировки» возвращает на «Главную» (до исправления закрывал приложение); сессия сохраняется после
  перезапуска приложения.
- Состояния: пустые состояния главной и «Тренировок» у нового клиента; при остановленном API —
  «Нет соединения с сервером» и «Повторить», после запуска API повтор загружает данные.
