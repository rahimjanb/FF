# Питание: AI Food Scanner, дневник, аналитика, консультант

Модуль раздела «Питание» в приложении клиента. Бэкенд: `backend/src/FitnessFormulasi.Api/Features/Nutrition`
и `Features/Ai`. Приложение: `mobile/lib/ui/client/nutrition`, `mobile/lib/data/nutrition_*.dart`.

## Как это работает

```
Фото ──> FoodImage (JPEG, размер, удаление EXIF) ──> AI Vision (IAiModelClient)
          │                                            │ JSON по строгой схеме: блюда, ингредиенты,
          │                                            │ граммы, способ приготовления — без калорий
          │                                            v
          │                         FoodRecognitionService: проверка JSON поле за полем
          │                                            v
          │                         FoodDatabaseService: ингредиент → продукт
          │                         (ключ каталога → поиск по названию → USDA API)
          │                                            v
          └──> MediaStorage         NutritionMath (Nutrition Engine):
               (фото на сервере)    значение на 100 г × граммы / 100, сумма, диапазон
                                                       v
                                    Экран результата: клиент правит граммы и состав
                                                       v
                                    «Добавить в дневник» → FoodDiaryService
```

Главные правила:
- **ИИ не считает калории.** Он определяет блюдо, ингредиенты, вес и способ приготовления. Калории, БЖУ,
  клетчатку, сахар, насыщенные жиры и натрий считает `NutritionMath` по базе продуктов. У каждого ингредиента
  хранятся вес, значения на 100 г и источник (USDA FDC id, штрихкод Open Food Facts, этикетка, рецептура).
- **Ответ ИИ проверяется.** Схема structured outputs ограничивает форму ответа. Затем `ParseVision` и
  `ParseLabel` проверяют каждое поле: тип, допустимые значения, диапазоны. Неизвестные ключи каталога
  отбрасываются, граммы и уверенность ограничиваются. Структурно неверный ответ запрашивается ещё раз, второй
  неверный ответ — ошибка `ai_invalid_response`. Строки очищаются от управляющих символов и разметки.
- **Ничего не выдумывается.** Ингредиент, которого нет ни в одной базе, остаётся без значений. Итог помечается
  «неполные данные», клиент выбирает продукт сам. Если внешняя база недоступна, это ошибка, а не нули.
- **Без ложной точности.** Вес с фото — оценка: ±15 % при высокой уверенности ИИ, ±25 % при средней, ±40 % при
  низкой. Масло и соусы ±50 %: их почти не видно. Диапазон калорий = Σ ккал × (1 ∓ погрешность). Вес, исправленный
  клиентом, ±10 %; упаковка по этикетке или штрихкоду ±5 %; типичная рецептура ±20 %. Калории округляются до целых,
  граммы БЖУ — до десятых.
- **Масло, соусы, способ приготовления.** Жир и соусы — отдельные ингредиенты с ролью `Fat`/`Sauce`, даже если
  их не видно, а способ приготовления их подразумевает (плов, самса, жареное). У них самая широкая погрешность.
  Если блюдо жареное, а масла среди ингредиентов нет, результат получает предупреждение `cooking_fat_missing`.
  В приложении есть кнопки «масла меньше / больше» (×0,5 / ×1,5 граммов жиров и соусов).
- **В дневник только с подтверждением.** Сканирование сохраняется в истории; запись в дневнике появляется
  только после «Добавить в дневник».

## Национальная кухня Узбекистана

Встроенная база (`Features/Nutrition/Data`, собирается скриптом `backend/tools/nutrition-data`):
- **314 продуктов** со значениями из USDA FoodData Central, SR Legacy (2018-04), по FDC id; значения не вводились
  вручную. Отсутствующие в USDA значения — `null`, не 0.
- **29 рецептур** 16 блюд: плов (ташкентский, самаркандский, ферганский), самса (тандырная, слоёная, с тыквой),
  манты (с бараниной, с тыквой), лагман (суповой, жареный), шашлык (баранина, говядина, курица, люля, печень),
  шурпа, норин, мастава, димлама, чучвара, ханум (с мясом, с картофелем), гумма (с мясом, с картофелем), лепёшка,
  сузьма, катлама, чак-чак. Состав — типичный рецепт на 1 кг готового блюда, в виде «как едят» (варёный рис,
  тушёное мясо). Значения на 100 г вычисляются из ингредиентов USDA, а не задаются числом.

Рецептуры используются тремя способами:
1. В промпте Vision как типичный состав: ИИ берёт его за основу и подстраивает под фото (больше мяса, без нута,
   видно масло).
2. Если ИИ узнал блюдо, но не разобрал ингредиенты, подставляется типичный состав, пересчитанный на увиденный вес
   (предупреждение `weight_uncertain`).
3. В ручном поиске: «плов 350 г» добавляется в дневник по рецептуре.

Заменители продуктов, которых нет в USDA (лепёшка — пита, сузьма — греческий йогурт, курдючный жир — бараний жир
и т. д.), и допущения по каждому блюду описаны в `backend/tools/nutrition-data/README.md`.

## Источники данных

| Источник | Что даёт | Ключ | Где в коде |
|---|---|---|---|
| Встроенная база (USDA SR Legacy) | Продукты и рецептуры, всегда доступны | не нужен | `NutritionSeeder` (загрузка при старте, по ключу) |
| USDA FoodData Central API | Поиск продукта, которого нет во встроенной базе | `FoodData__UsdaApiKey` (бесплатно, api.data.gov) | `UsdaFoodSearchSource : IFoodSearchSource` |
| Open Food Facts API v2 | Товар по штрихкоду | не нужен | `OpenFoodFactsSource : IBarcodeProductSource` |
| Этикетка (фото, ИИ) | Значения, напечатанные на упаковке | ключ ИИ | `FoodRecognitionService.ReadLabelAsync` |
| Клиент | Свой продукт или рецепт | — | `FoodDatabaseService.CreateOwnAsync`, `SaveRecipeAsync` |

Внешние источники скрыты за интерфейсами `IFoodSearchSource` и `IBarcodeProductSource`: поставщика можно
заменить, не меняя бизнес-логику. Ответы кэшируются в БД как продукты: товар по штрихкоду — на 30 дней,
«не найден» — на 3 дня. Если Open Food Facts недоступен, отдаётся устаревший кэш, а без кэша — ошибка
`food_db_unavailable`.

Этикетка: kJ переводятся в ккал (÷ 4,184), соль в натрий (÷ 2,5). Значения «на порцию» пересчитываются на 100 г.
Если энергия не сходится с БЖУ (4/9/4 ккал на грамм, допуск 20 %), этикетка считается прочитанной неверно, и
приложение просит переснять. Продукт с этикетки сохраняется как свой продукт клиента вместе со штрихкодом:
следующее сканирование штрихкода найдёт его.

## ИИ-провайдер

`IAiModelClient` — единственная точка, где бизнес-логика встречается с ИИ. Реализации:
- `AnthropicAiClient` — Claude через официальный SDK `Anthropic` (NuGet). Structured outputs для фото и
  этикеток, ручной цикл инструментов для консультанта, кэширование промпта (каталог продуктов не меняется между
  запросами). Повторы при 408/409/429/5xx и сетевых ошибках делает SDK (`Ai__MaxRetries`), с общим таймаутом
  `Ai__TimeoutSeconds`. Если модель отказывает по своей политике, API повторяет запрос на запасной модели
  (server-side fallback, `Ai__RefusalFallback`).
- `DisabledAiClient` — когда провайдер не настроен: ИИ-функции отвечают `ai_not_configured`, приложение
  показывает «ИИ-анализ не подключён», дневник, штрихкоды и поиск работают.
- В тестах — `FakeAi` с заданными ответами: реальные токены не расходуются.

Другой провайдер подключается новой реализацией `IAiModelClient` и строкой в `Program.cs`.

`AiGateway` оборачивает каждый запрос:
- дневные лимиты клиента по видам запросов (фото, этикетки, консультант, отчёты);
- месячный бюджет на весь клуб (`Ai__MonthlyBudgetUsd`): по достижении — `ai_budget_exceeded`;
- запись каждого запроса в таблицу `AiUsage`: модель, токены (в том числе кэшированные), стоимость в USD по
  ценам из настроек, время, успех или код ошибки;
- строку в логе с теми же данными.

Ответ, не прошедший проверку, помечается неуспешным и не расходует дневной лимит клиента.

Ключ API — секрет: только переменная окружения или user-secrets, в коде и `appsettings.json` его нет.

### Что уходит в ИИ

| Функция | Отправляется | Не отправляется |
|---|---|---|
| Фото еды | JPEG без EXIF/XMP/IPTC (нет геолокации, модели телефона, времени), подсказка клиента, каталог продуктов | имя, телефон, e-mail, id клиента |
| Этикетка | JPEG без метаданных | то же |
| Консультант, отчёты | вопрос, история чата, данные, которые модель запросит инструментами: профиль питания (цель, пол, возраст, рост, вес, активность, норма, ограничения, аллергии), дневник, периоды, сканирования, даты тренировок и посещений, поиск продуктов | имя, телефон, e-mail, имена тренеров |

Перед первой ИИ-функцией клиент даёт отдельное согласие в приложении (`POST /api/nutrition/ai-consent`,
запись в журнале аудита). Без согласия сервер отвечает `409 ai_consent_required`. Этого требует правило App Store
5.1.2(i) о передаче персональных данных стороннему ИИ. Согласие можно отозвать.

## API

Все маршруты — только для роли `Client`. Данные выбираются по профилю из токена: чужие сканирования, записи,
фото, продукты и рецепты отвечают `404`.

| Метод и путь | Что делает |
|---|---|
| `POST /api/food-scanner/analyze` | Фото (multipart `photo`, JPEG ≤ 6 МБ, 320–4096 px) и подсказка `hint` → блюда и пищевая ценность |
| `POST /api/food-scanner/label` | Фото этикетки (+ `barcode`) → свой продукт клиента |
| `POST /api/food-scanner/barcode` | `{code}` → товар; `404 barcode_not_found` |
| `GET /api/food-scanner/history` | История сканирований (страницы) |
| `GET /api/food-scanner/result/{id}` | Результат сканирования |
| `PUT /api/food-scanner/result/{id}` | Правка блюда (граммы, ингредиенты, название) → пересчёт |
| `DELETE /api/food-scanner/result/{id}` | Удалить сканирование и фото |
| `GET`, `DELETE /api/food-scanner/result/{id}/photo` | Фото / удалить только фото |
| `GET /api/food-diary?date=` | День дневника: приёмы пищи, итоги, норма |
| `POST /api/food-diary` | Запись: продукты, рецепты или ингредиенты сканирования |
| `GET`, `PUT`, `DELETE /api/food-diary/{id}` | Запись дневника |
| `POST /api/food-diary/{id}/repeat` | Повторить запись (сегодня) |
| `GET /api/food-diary/recent` | Недавние блюда для повтора |
| `GET /api/nutrition/daily?date=` | День: итоги, остаток нормы, по приёмам пищи, тренировки |
| `GET /api/nutrition/weekly?end=` | 7 дней |
| `GET /api/nutrition/monthly?month=yyyy-MM` | Календарный месяц |
| `GET /api/nutrition/report?period=Day\|Week` | ИИ-отчёт; повторно берётся из кэша, пока данные не изменились |
| `POST /api/nutrition/consultant/chat` | ИИ-консультант |
| `GET`, `PUT /api/nutrition/profile` | Цель, рост, вес, активность, ограничения → дневная норма |
| `POST`, `DELETE /api/nutrition/ai-consent` | Согласие на ИИ-анализ |
| `GET /api/nutrition/foods/search?q=` | Поиск продуктов и блюд (рус., узб., англ. названия и синонимы) |
| `GET`, `POST`, `DELETE /api/nutrition/foods[/{id}]` | Продукт / свой продукт |
| `GET`, `POST`, `PUT`, `DELETE /api/nutrition/recipes[/{id}]` | Рецепт / свой рецепт |

Коды ошибок: `ai_not_configured` 503, `ai_consent_required` 409, `ai_unavailable` 503, `ai_rate_limited` 429,
`ai_quota_exceeded` 429, `ai_budget_exceeded` 503, `ai_invalid_response` 502, `ai_refused` 422,
`scan_in_progress` 409 (предыдущее фото ещё анализируется), `photo_invalid_format`, `photo_too_large`,
`photo_bad_size` 400, `barcode_not_found` 404, `food_db_unavailable` 503, `item_source_required`,
`item_not_found`, `invalid_date` 400.

Защита от повторов и перегрузки:
- то же фото с той же подсказкой в течение 7 дней возвращает прежний результат (`reused: true`) без нового
  запроса к ИИ, сравнение по SHA-256 очищенного JPEG;
- у клиента одновременно анализируется одно фото;
- ограничение частоты: `ai` — 6 запросов в минуту на пользователя, `lookup` (штрихкоды, поиск) — 60.

## Дневная норма

Формула Миффлина — Сан Жеора × коэффициент активности (1,2 / 1,375 / 1,55 / 1,725 / 1,9). Для похудения −15 %,
для набора +10 %. Не ниже 1200 ккал для женщин и 1500 ккал для мужчин.
- Белок: 1,6 г/кг, при похудении и наборе 1,8 г/кг (позиция ISSN: 1,4–2,0 г/кг), не более 35 % энергии.
- Жиры: 30 % энергии, при наборе 25 % (диапазон DRI 20–35 %).
- Углеводы: остаток.
- Клетчатка: 14 г на 1000 ккал. Натрий: не более 2300 мг (Dietary Guidelines for Americans 2020–2025).

Клиент может задать свою норму калорий. Пол и дата рождения берутся из профиля клиента: это те же поля, что на
экране профиля.

При удалении аккаунта удаляется всё питание клиента: сканирования и файлы фото, дневник, свои продукты, рецепты
и штрихкоды, профиль питания, итоги, отчёты. Записи `AiUsage` остаются без привязки к человеку — это история
расходов.

## Ограничения

- Вес по фото — оценка. Точнее всего, если в кадре есть тарелка или приборы, а клиент проверит граммы.
- Встроенная база — общая USDA, без узбекских промышленных продуктов. Узбекские блюда считаются по типичным
  рецептурам; домашний рецепт может заметно отличаться (особенно количество масла в плове).
- Open Food Facts заполняется сообществом. Узбекских товаров в нём немного, а данные бывают неполными: например,
  аллергены записаны как «следы». Если товара нет, приложение предлагает сфотографировать этикетку.
- Поиск по USDA API (продукты вне встроенной базы) работает только с ключом `FoodData__UsdaApiKey`.
- Учёта воды нет: такой функции в приложении не было.
- Приложение только в тёмной теме: светлой темы в проекте нет, раздел следует общей теме.
- Расчёты не являются медицинской рекомендацией; консультант направляет к врачу при заболеваниях.
